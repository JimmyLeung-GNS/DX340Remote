# Connection reports

The shared phone app has a deliberate troubleshooting action in **Setup → Connection help**: **Save connection report** on Android or **Share connection report** on iPhone. This does not connect, authorize, retry, change playback or adjust volume. The regular UI snapshot does not include the journal, so collecting it adds no library/queue rebuild notifications.

History belongs to the current native model instance and is cleared by process restart. Each native model creates a random instance identifier, reused by its exports for safe correlation; it is not a device, Bluetooth or controller identity. The default limit is 256 requests and 256 connection transitions. Eviction counters expose missing earlier history.

Format version 1 contains allowlisted operation/source/error/connection categories, request IDs and relative monotonic milliseconds. Unknown categories become `OTHER`/`other`. Music metadata, command arguments, item IDs, paths, artwork, Bluetooth identities, host epochs and credentials are excluded. App/OS versions and generic device model identify the software environment. Android additionally hashes its own installed base APK, outside the BLE callback thread. No source storage is scanned.

The native journals map the actual wire source IDs `com.ibasso.music` and `com.apple.android.music` to the fixed report categories `mango` and `apple`. Short category names remain accepted; unknown package names, lookalikes and case variants become `other`. This affects diagnostics only; wire IDs and source routing are unchanged. Earlier builds exported real package IDs as `other`; preserve those reports and do not infer or rewrite their source categories afterward.

Connection entries record native setup-phase assignments; the root `connectionPhase` separately captures current derived permission/radio/authorization readiness. This is not continuous radio observation. Unsolicited state events are not matched request receipts and do not create latency samples. In particular, a dispatched-only action followed by a later state event does not acquire an inferred observed-state duration in this journal.

Each request records `startedMs`, nullable `firstWriteSubmittedAfterMs`, nullable `writeAcknowledgedAfterMs`, `accepted`, nullable `acceptedAfterMs`, nullable `finishedAfterMs`, `result`, `terminalApplied`, `hostOutcome` and nullable `error`. A duplicate/late reply cannot overwrite its first protocol receipt. Unknown or changed-host replies are rejected before journaling. Clock regression produces null, never a fabricated duration. Timings start at native send registration, before encoding/queued writes. Protocol timings end at matched decoded replies after reassembly.

Added1 November2026, `firstWriteSubmittedAfterMs` records the first frame's platform submission, independently of the last frame's successful acknowledgment. On Android it is recorded only after [writeCharacteristic](https://developer.android.com/reference/android/bluetooth/BluetoothGatt#writeCharacteristic(android.bluetooth.BluetoothGattCharacteristic,%20byte[],%20int)) returns success (or true on the older API); a rejected call never records it. On iOS it follows the first [CoreBluetooth withResponse write invocation](https://developer.apple.com/documentation/corebluetooth/cbperipheral/writevalue%28_%3Afor%3Atype%3A%29); that API has no immediate acceptance return, so this is invocation evidence, not Android-style acceptance proof. Neither event proves reception, completion of every frame, a protocol result or playback. A known submission with no final ACK at local loss identifies an interrupted logical write; it does not identify an over-the-air packet boundary. First-submission callbacks do not advance the FIFO, repeat on later frames, retry a failed write or revive abandoned/evicted rows. A regressed first-submission clock stays null even if a duplicate observation follows. Legacy format1 reports may omit this optional field and remain unknown; the analyser validates/merges it separately and never infers it from ACK/reply timings. Android's diagnostic log emits only the operation and random request ID at this event, never arguments, music metadata or Bluetooth identities.

Added1 November2026, `writeAcknowledgedAfterMs` ends at the successful native write-response callback for the request's **last frame**, after all preceding frames succeed. It includes encoding, queue wait and callback scheduling; it is not a per-frame RF round trip, UI-tap or acoustic measurement. [Android onCharacteristicWrite](https://developer.android.com/reference/android/bluetooth/BluetoothGattCallback#onCharacteristicWrite(android.bluetooth.BluetoothGatt,%20android.bluetooth.BluetoothGattCharacteristic,%20int)) and [CoreBluetooth withResponse completion](https://developer.apple.com/documentation/corebluetooth/cbperipheraldelegate/peripheral%28_%3Adidwritevaluefor%3Aerror%3A%29-4f5ea) provide the platform events. An intermediate frame, failed write, cleared queue or missing callback never completes the logical write. A write acknowledgement does not set `accepted`, apply a result or establish playback. A protocol result may arrive before the write callback; its first terminal timing stays unchanged while the separate write timing is filled. Late callbacks after local abandonment cannot revive that request. Legacy reports lack this optional format1 field and remain unknown, never inferred from a reply.

`ACCEPTED` means the host accepted the request. A terminal receipt can still be ignored by context/payload guards; `terminalApplied` becomes true only after the native client processes it. `hostOutcome=dispatched` is distinct from `observed`. Neither proves audible playback. Timeout, send failure, connection loss and session reset finalize unfinished entries without resending operations.

Android creates a unique app-owned JSON file under `Download/DX340Remote` with MediaStore, publishing only after a successful bounded write. It requests no additional storage permission. This follows [Android shared-media guidance](https://developer.android.com/training/data-storage/shared/media). iPhone prepares at most three own temporary JSON files and opens the native [activity controller](https://developer.apple.com/documentation/uikit/uiactivityviewcontroller/), anchored for iPad. The notice says to choose a destination; presentation is not a claim that the owner saved or shared a file. No destination or recipient is chosen automatically.

The report is at most 256 KiB. Native export is single-flight; a failure permits another deliberate attempt. The shared UI keeps report progress/errors separate from connection/source status.

## Verification and limits

The Kotlin and Swift journals consume the same12 fixtures for protocol/write timing order, duplicates, privacy categories, losses, eviction, clock regression, duplicate registration and actual wire source IDs. Four shared write-queue fixtures cover final-frame completion, FIFO, cancellation and atomic bounds; a queue/journal integration test checks per-request queue wait without implying playback. Sustained-operation tests cover bounded memory; Android JSON tests check explicit nulls survive serialization. Flutter tests check explicit invocation, single-flight, failure/retry, disposal and the collapsed-help action on both platform styles.

The iOS CI developer-only `report_export_probe.dart` uses the real native bridge and UIKit with no BLE/source fixture, correlates a unique launch marker and native model instance, checks an empty request history and the strict report keys, then captures the share sheet. The existing EXIT trap rebuilds/reinstalls/relaunches ordinary `main.dart`, including after failure. This probe is never imported by the production entrypoint.

Builds, simulator exports and fixture timings do not pass T04. Physical exports from the actual phones, decoded ACCEPTED versus terminal/applied outcomes, source-state observation and listening remain separate required evidence. Do not relabel old physical results as results for a newly built candidate.

## Summarizing exports

Run `python scripts/summarize-connection-reports.py <first.json> <second.json>` with explicit export paths. The standard-library tool rejects mixed reported build/platform/OS environments, conflicting request identities/receipts, duplicate JSON keys and oversized/unexpected report fields. Separate Android model sessions require the explicit `--allow-multiple-sessions` option and an identical APK digest/OS environment. iPhone reports have app versions but no binary digest, so distinct iPhone model sessions remain separate even with this option; retain external source/build provenance. Reused development version numbers do not establish binary identity. Request IDs are deduplicated with their model instance, so process restarts do not collide. Repeated eviction counters use the maximum per session rather than being added on every export.

The output groups operations by source and separates ATT logical-write acknowledgements, accepted receipts, terminal replies, applied successful results and host-observed applied results. The analyser reads both legacy rows and the optional write field; overlapping exports can add a later write callback without replacing the first protocol receipt. Conflicting known write timings and write callbacks attributed after local termination are rejected. Timeouts/losses/errors remain outcome counts. Percentiles use nearest rank; missing or invalid-clock samples do not become zeros. Empty reports retain zero samples and null percentiles. Eviction totals describe native history-window evictions; some rows may have been recovered from an earlier export, so they are not a count of missing rows in the merged union. Every summary says `physicalT04=NOT_ADJUDICATED`: reports alone cannot establish the complete controlled source/phone/local-track matrix or audible output. Overlapping exports do not inflate the sample count.

Run the analyser's synthetic checks with `python -m unittest discover -s scripts/tests -p test_connection_reports.py -v`. Keep raw exports and generated summaries under ignored `artifacts/`, with sanitized device/build/test conditions in `docs/test-results/`.
