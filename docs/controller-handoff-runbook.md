# Two-controller handoff acceptance

Status: **NOT TESTED on two physical controllers.** Implementation beta only. This is separate from switching Mango/Apple playback sources and from source-local listening results.

Use the companion and shared phone apps from the same handoff checkpoint. Keep the original debug signing identity for in-place updates. Record SHA256s, phone models/exact OS builds, DX340 firmware/Android build, source versions, output/amp/gain and battery conditions. Current31 October inventory is DX340 plus Pixel9a; no second phone or physical iPhone is attached. Re-inventory on continuation. Preserve the owner's Pixel/JIMMYAH approvals and OS bonds; a hypothetical revocation case below is not permission to remove either retained development grant.

1. Enroll new phone A/B separately using Companion Set up first phone or Set up a new phone, shared Setup → Connect, matching system codes if prompted and identified local approval. Updated shared clients observe approval automatically; repeat Connect explicitly after expiration. Retained approved phones need no new enrollment. Disconnect live transports before enrolling a new controller, preserving saved grants/bonds. Do not reapprove a revoked identity implicitly. For the offline case record original radio settings, disable Wi-Fi/cellular as specified, then restore original settings afterward.
2. At a comfortable low level, start a known track in Mango locally. Connect A and observe current state. B connects, completes HELLO/AUTHORIZE and receives the busy response. B must have no source control or metadata access until ownership is granted. No new pairing window/local approval should be needed for this already approved identity.
3. On B, open Setup and tap **Take control on this phone** once. A should report control moved, disconnect and stop auto-reconnecting. B should receive fresh state/sources and enable only supported actions. Listen for continuity and inspect track/source/position/output/volume. Handoff must not itself select a source, play/pause, skip, seek or alter volume.
4. Issue deliberate controls on B; confirm the correct source and audible result. Reconnect A and explicitly transfer back. Repeat ten times, recording grant/notice/disconnect timings and whether DX340 handling was required. Do not label the route stable from one success.
5. During a pending browse/artwork/source validation on A, transfer to B. Drop unsent A replies, invalidate its lease and deny late dispatch/cache publication. A source action already dispatched before transfer cannot be undone; record actual ordering/outcome separately. Test duplicate handoff request IDs, a stale ownership revision, a reused grant after disconnect and same-ID late mutation cleanup. Never automatically replay a failed request.
6. With a separately authorized identified test controller, revoke B while it is the bootstrap peer and again while it owns control. This case stays NOT TESTED until that authorization/hardware exists; do not use the retained Pixel/JIMMYAH grant implicitly. Confirm metadata/command denial and immediate closure while other approvals/OS bonds remain. Repeat permission loss, host restart and range recovery separately. Do not restore revoked access without a fresh identified local approval.
7. Leave B at the busy screen for over60 seconds; it must disconnect with controls disabled. A must remain controlling. Legacy displaced clients should be closed after10 seconds. These are scheduled deadlines; measure actual sleep/main-thread timing rather than assuming wall-clock guarantees.
8. Test a missing indication completion in an isolated diagnostic run. The host must close the GATT server and all authorization/queued data, report restart instructions and submit no further indication until reset. Stop/start remote control on DX340 and reconnect deliberately. Confirm music keeps playing; a transport error must not change playback or volume.

Repeat the relevant steps with Apple Music downloaded playback offline, identifying any screen-on/unlocked UI browsing. Repeat after normal phone/DX340 sleep and with large libraries. Capture raw radio/application logs separately from human listening answers. This does not replace the remaining T01–T16/Watch, audio-quality, battery or one-hour-walk acceptance.

If DX340 cannot keep two real central links, record the actual error and keep disconnect-first operation available. Do not add Wi-Fi or silently promise direct Watch handoff. Watch work still waits for stable physical phone operation.
