# Phone connection acceptance

Status: NOT TESTED on separate physical phones. Flutter UI tests, DX340-only launch and iPhone simulator checks do not pass these steps. Use this with compatibility-matrix.md/T01–T18; keep Android and iPhone results separate.

Record phone model, exact OS/build, app version/commit, DX340 firmware/build, Mango/Apple versions, AMP15 output and APK/signing identity. Do not change volume during connection testing. Start with the verified source already playing at the user's comfortable level.

1. Install the shared phone build with the same signing identity. On Android, grant Nearby Devices and notification access in Setup. On iPhone, grant Bluetooth. Start companion, open its pairing window, Find DX340, connect, accept authenticated OS pairing, approve the pending controller on DX340, retry authorization. Record each prompt/outcome; no approved phone means controls must stay disabled.
2. Turn Wi-Fi off on both devices and cellular data off on the phone. Record these states independently. Browse native Mango albums and select a track; confirm title/source state and human audio separately. Apple UI-assisted selection must be an offline downloaded track absent from the complete prior queue; wake/unlock DX340 for that optional mode. The new optional Mango folder adapter has a local user-confirmed WAV result; test its Local folders entry separately over each phone's BLE path. Neither local result passes this phone matrix.
3. Repeat discovery/connection ten times, recording time to visible ready/authorization and failures. Reconnect must refresh state and leave source playback intact. Sending a command or seeing an ACK is not observed/audible playback proof.
4. Lock the phone for30 minutes while music plays, then open it and refresh. Repeat with DX340 asleep. Native transport is tested separately from screen-on assisted browsing. Repeat after a30-minute pause. Record foreground/background transitions and whether a service notification is present on Android.
5. Walk out of range and return ten times. Record time to link/authorization/state recovery. While disconnected, attempt one disabled playback control: it must not later replay. Reconnection may make bounded attempts; if Setup requires a deliberate retry, record that instead of marking automatic recovery passed.
6. Toggle phone Bluetooth off/on, then DX340 Bluetooth off/on. Record whether automatic recovery, explicit Find/Connect or restarting the companion is needed. Revoking Android Nearby Devices or iPhone Bluetooth access must disable control with a recovery message; granting it again must not replay old commands.
7. Revoke the phone in the companion during a pending browse/action. Observe denial/current state; later replies must not reauthorize or enable stale controls. Test an unapproved phone independently. OS bonds and companion approval are separate.
8. Recreate the Android Activity / background-foreground the iPhone. Deliberately terminate each controller process, then reopen. Do not confuse a user force-stop with OS suspension. Confirm music kept playing and the UI recovers current state. Repeat source change while a browse is loading; old library rows must not become actionable for the new source.
9. Run the planned one-hour walk, matched battery tests,100 controls per source/phone, source-format and complete browsing matrices. Record actual counts, failures, recovery steps and audio observations. Test app upgrade while preserving approval/cache, and separately record clean-install permission behavior.

10. Elapsed time: use the new host/phone builds with matching signing identity. While playing, compare the labelled estimate with source position; pause, resume, seek where supported, change track/source and reach track end. A paused source with a nonzero advertised speed must stay frozen. Background/lock and return: the estimate must stop immediately and wait for a fresh state, then recover without replaying playback. Disconnect/reconnect and delayed artwork/library/status events must not restart an old clock. Check both phones independently; source state, actual listening and BLE recovery are separate results. No periodic state requests are added solely for elapsed display.

11. Queue pagination: with a source queue above50 entries, refresh Queue on each physical phone, use Next queue page to reach its final entry and Start of queue to return. Compare the displayed ranges/total and every returned item against the source queue; with101 entries expect windows1–50,51–100,101. Each continuation uses the previous revision. Change the source queue between pages: the next request must report a stale queue and require refresh, retaining no actionable rows from the failed response. During a read, old rows/duplicate reads stay disabled. Disconnect/revoke/change source during a pending page; its late reply must not populate the new source. Select an item beyond50, checking correct source state and human audio separately. A source-local debug pagination check or widget fixture does not pass these phone steps. On DX340 with both apps paused and the debug companion running, scripts/verify-queue-pagination.ps1 provides a repeatable read-only own-adapter check without BLE/instrumentation.

Store reports under docs/test-results; raw diagnostic logs/screenshots stay in artifacts. Each row is VERIFIED, FAILED, BLOCKED or NOT TESTED with the exact device/app combination. Do not fill missing cases from simulator or source-only results. Watch remains gated on stable phone evidence.

12. Pending assisted browsing: on each phone start an Apple/Mango browse, then put DX340's screen off or select the other source before it completes. The old request must stop with an actionable error; its navigation tokens must not work after returning, and a fresh browse must recover without playback replay. Test actual permission/approval revocation and radio loss separately. scripts/verify-assisted-interruptions.ps1 provides source-local screen-off and timed in-process-source-change checks with both apps paused, tagged pending/finished reports and final wake/control-target restoration. It does not pass phone BLE, controller revocation, secure-lock or long-sleep acceptance.
