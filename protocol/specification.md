# DX340 BLE protocol v1 — diagnostic beta

Storage boundaries reuse existing v1 sourceEpoch/STALE_LIBRARY behavior. On a public storage-volume event the companion retires both source epochs before cancelling native/assisted browse requests and clearing native item proofs, revision baselines, UI tokens/downloaded context and volume proof; the changed epochs also retire queue revisions. Controllers must remove old library/queue actions when the source epoch changes and explicitly fetch fresh data; no playback is replayed. Storage observation failure disables arbitrary library/queue selection and reports why, while transport controls remain separately capability-gated. This changes no wire fields. [Current scoped tests](../docs/test-results/2026-10-30-storage-invalidation.md) include synthetic boundaries over real Pixel BLE; actual SD event delivery is not yet verified.

No audio is sent over this service. All JSON is UTF-8. Commands operate installed DX340 source apps through public interfaces. Service UUID: `e7e01000-4a76-4b53-9c8f-c7a12b00d340`. INFO ends `1001`, RX ends `1002`, TX ends `1003` with the same suffix. Full constants live in Kotlin Wire and Swift Wire.

## GATT and authorization

INFO is read; RX is write-with-response; TX is indicate with CCC `00002902-0000-1000-8000-00805f9b34fb`. INFO/RX/CCC require encrypted authenticated (MITM) access through the Android Bluetooth stack. TX sends confirmed indications. Both peers serialize operations. Discovery advertises only service UUID. Default ATT payload is 20 bytes; host uses MTU minus 3; iPhone uses maximumWriteValueLength(for: .withResponse). Each capacity is capped at 512, never assumed.

Delayed results/state replies recheck current bond, local approval and authenticated session before sending. Disconnect clears pending outbound frames and subscriptions immediately; an indication already submitted to the OS cannot be recalled. Stopping the host invalidates its authenticated session before source/transport teardown. Source mutations recheck closed/permission/source/approval guards at final dispatch. These software rules do not replace physical revocation/security tests.

Host indications are serialized through a bounded confirmed-frame queue. Each submitted frame has a10-second Handler-scheduled completion deadline; sleep/main-thread scheduling can delay wall-clock expiry. Error completion, immediate submit failure, overflow, unsubscribe or disconnect clears that peer's queued frames and logical authorization. Disconnect retains an in-flight tombstone until completion. Missing completion closes the whole GATT server; stop/start remote control on DX340 to recover. Successful completions cancel their deadlines; stale scheduled timers cannot close a new transfer. Reconnection never replays old frames or playback. Android completions have no frame ID, so delayed same-peer callbacks across reconnect and all actual timing/radio behavior still require physical tests.

Open a 60-second pairing window on DX340. Accept OS pairing and visibly approve the bonded controller in the companion. HELLO returns protocol/host epoch only. AUTHORIZE returns source metadata only after approval. Approval refers to the OS bonded identity, using Android's resolved bond address; a display name or an unbonded address is never sufficient. Maximum eight approvals. Revocation denies subsequent messages and disconnects the affected peer. At most two transports are admitted, with one controlling authorization lease. The second must already be approved and OS-bonded, even during pairing. New-controller enrollment requires the existing transports to disconnect first. Actual two-central hosting, MITM/security and identity resolution across iPhone address changes are NOT TESTED. Do not claim production authentication from these API flags alone. No custom cipher, reusable PIN or application secret is sent.

### Client setup recovery

Client recovery also bounds unfinished setup: Kotlin/Swift start a60-second monotonic deadline after protected subscription. Authorization cancels it; disconnect/new-attempt generations invalidate stale timers. Foreground entry, requests and replies recheck elapsed time after suspension. LOCAL_APPROVAL_REQUIRED pauses automatic reconnect while retaining the live approval opportunity; a successful authorization restores normal reconnect policy. Expiration closes the unfinished client link and clears pending commands without revoking saved approvals/bonds or replaying playback. This is independent of the host's security/bootstrap windows and does not extend them or promise exact wall-clock callback delivery. Shared connection-setup-deadline.json fixtures cover cancellation, old tickets, suspension and rollback; physical unapproved-current-Pixel/iPhone expiration remains untested.

### Assisted page lifetime on clients

A Mango assisted PLAY_ITEM consumes the source UI frame even when its folder still appears on screen. Clients bind the request to the actual Mango source, epoch and rendered revision; terminal reply, timeout or connection loss retires only that matching page. Retired rows remain visible but cannot issue play, folder, Back or page actions. Explicit fresh-root BROWSE remains available; it does not replay playback. Apple and native Mango item routes are unchanged. The client-only `library.invalidated` snapshot marker is presentation state, not a new wire command or host authorization signal. Shared assisted-page-use/assisted-selection-eligibility fixtures cover stale/duplicate replies, newer contexts, loss and route admission. Physical acceptance remains separately recorded.

### Explicit controller handoff (additive v1 beta)

A second approved controller performs HELLO/AUTHORIZE. While another controller owns control, AUTHORIZE returns ERROR with `code:CONTROLLER_BUSY` and opaque `ownershipRevision` (1–64 ASCII letters/digits/hyphens), without source metadata or owner identity. The phone pauses automatic reconnect and offers **Take control on this phone** in Setup. Only an explicit tap consumes the native host-bound proposal and sends REQUEST_CONTROL with current hostEpoch and args.ownershipRevision. A disconnect, new HELLO or invalid bridge response clears availability. Older clients/hosts need disconnect-first operation; no automatic compatibility fallback requests ownership.

The host compares the current ownership revision, grants a fresh authorization lease and invalidates old asynchronous work before returning RESULT with authorized/state/sources to the new owner. A stale comparison returns STALE_CONTROL. The old approved peer receives fixed unsolicited `CONTROL_CHANGED` / `data:{code:CONTROL_MOVED}` with empty id; unsent old metadata is dropped. Updated clients disconnect and suppress autoreconnect. A displaced legacy client is closed after10 seconds; an unauthenticated bootstrap connection expires after60 seconds (Handler/main-thread deadlines). Already submitted OS data cannot be recalled. Handoff makes no source-selection, playback or volume request; a source action dispatched before handoff may already have occurred and cannot be undone.

REQUEST_CONTROL shares the per-controller command ledger. A duplicate grant is replayed only while that exact grant lease remains current; after displacement/disconnect it returns CONTROL_REQUEST_USED and cannot reacquire control. A fresh AUTHORIZE obtains a new proposal if needed. Failed requests/timeouts never retry automatically. Mutation cleanup uses unique gate leases, so an old callback with a reused request ID cannot release a newer mutation. Request rate is20/second per connected identity. Each link has independent framing IDs, MTU and reassembly; all host indications share one bounded serializer (12000 frames, control before background). Disconnect keeps an in-flight tombstone until the OS callback. If no callback arrives by10 seconds, the entire GATT server closes, all leases/queued data clear, and the owner must stop/start remote control on DX340. A deadline does not authorize another OS submission. Repeated ambiguous CONNECTED callbacks fail closed. Radio/late-callback timing and playback continuity remain physical acceptance gates. [Android callback sequencing](https://developer.android.com/reference/android/bluetooth/BluetoothGattServerCallback#onNotificationSent(android.bluetooth.BluetoothDevice,int)).

Host authorization is scoped to an in-process connection/session lease as well as the bonded/approved identity. Requests retain that lease through asynchronous source validation and replies. Disconnect/revocation/host destruction invalidates it; reauthorizing the same address cannot revive old work. Repeated AUTHORIZE within one uninterrupted authorized session is idempotent. Local per-controller revocation removes only the selected app approval and disconnects that peer; OS bonds/other approvals and host-epoch deduplication ledgers remain. Revoke-all also closes the pairing window. Actual authenticated/revoked-controller radio behavior remains physically unverified. These rules add no wire fields/version.

## Frames

Each characteristic value is at least 9 bytes: 8-byte header and nonempty payload. Big endian header: magic byte `44`, version `01`, 16-bit message ID, 16-bit zero-based chunk index, 16-bit chunk count. Chunks are strictly ordered per ID. Completed messages contain at most 65,536 bytes; four incomplete messages per connection; expiry after10 seconds without valid sequential progress or60 seconds total, on a monotonic clock. A backwards clock invalidates the partial. Only a valid next fragment advances its activity time; other messages and malformed/duplicate fragments cannot keep it alive. Clear assemblies and queued controls on disconnect. Malformed/out-of-order/oversized fragments are rejected; ATT errors are distinct from JSON errors. Message IDs wrap independently of request IDs. Shared UTF-8 fixtures: fixtures/framing.json. This progress policy replaces the earlier10-second total expiry after a physical53-fragment artwork transfer exposed that limit. Frame/envelope bytes and v1 IDs are unchanged; older receivers can still fail on slower bulk transfers until upgraded.

## Envelope

Requests: `{v:1,id:UUID,type:operation,hostEpoch:string,source:string,sourceEpoch:string,args:object}`. HELLO and AUTHORIZE bootstrap without a known host epoch. REQUEST_CONTROL requires current hostEpoch, bond and approval, and the explicit comparison above. All other requests require current authorization and hostEpoch. Source-scoped operations require the selected package ID and current sourceEpoch. Session token changes generate a new sourceEpoch. Request IDs are 1–64 ASCII alphanumeric/hyphen characters. Request rate is bounded at20 per second per connected identity; outbound frames are bounded. Source metadata is bounded; oversized encoded replies return RESPONSE_TOO_LARGE rather than invalid JSON.

Native Mango selection verification changes also advance sourceEpoch when the effective native capability changes. Clients clear old library/queue/navigation state on that event; old revisions are rejected. Same-session parent proofs remain refreshable and selections still re-read current native metadata. Repeated confirmation of an unchanged capability does not advance the epoch. Media-session callback ownership is separate: late callbacks from a replaced or closed session cannot retire a newer session or publish its state.

Replies: `{v:1,id:requestID,hostEpoch:string,type:HELLO|ACCEPTED|RESULT|STATE_CHANGED|CONTROL_CHANGED|ERROR,data:object}`. STATE_CHANGED and CONTROL_CHANGED are unsolicited with an empty ID. ACCEPTED means validation/dispatch is pending, never audible success. A mutation RESULT with `outcome:dispatched` confirms only that the public transport API was invoked. Observed state follows separately. A12-second controller timeout means unknown outcome; do not automatically retry mutations or handoff. GET_ARTWORK has a75-second pending-reply budget for bounded bulk delivery. PLAY_ITEM with an opaque mango-ui: item has a30-second observation budget: source handoff can take3.5s and assisted folder preparation is independently bounded at20s. Native/Apple selections and other controls retain12s. These client budgets do not extend host authorization, source action deadlines, per-frame watchdogs or no-replay behavior. Longer observation is not a latency acceptance result. Shared Kotlin/Swift contract: fixtures/reply-budgets.json.

Duplicate IDs in the same authenticated controller/host epoch return cached results or pending, never execute again. Different content under the same ID yields REQUEST_ID_REUSED. The beta ledger holds 2,048 IDs per approved controller and does not evict: SESSION_LIMIT requires a companion restart and new host epoch. Exactly-once execution across crashes is not claimed. Reconnect clears unsent operations, performs HELLO/AUTHORIZE, then observes state; it must not change playback or volume.

## Implemented operations

| Operation | Arguments / reply |
|---|---|
| HELLO, AUTHORIZE | Bootstrap; local approval required for AUTHORIZE |
| REQUEST_CONTROL | args.ownershipRevision from a current CONTROLLER_BUSY response; approved/bonded identity and hostEpoch required; no playback command |
| LIST_SOURCES, GET_CAPABILITIES | sources array: IDs, versions, epochs, per-action capabilities and browse probe |
| GET_STATE, SUBSCRIBE_STATE | state object; observed metadata/playback/capabilities |
| SELECT_SOURCE | args.source changes target; does not launch/play automatically |
| SET_PLAYING | args.playing explicit boolean; advertised action or exact-version physically tested desired-state adapter |
| NEXT, PREVIOUS | Individually capability gated |
| SEEK | args.position milliseconds, bounded by source duration |
| BROWSE | args.parent nullable root, page >=0, revision; 25 items per page, max 50; source/revision-scoped IDs |
| PLAY_ITEM | args.item previously browsed ID and args.revision; requires canPlayItem |
| GET_QUEUE | optional args.offset (default0), args.revision required after offset0; up to50 source queue items with revision/offset/total/nextOffset |
| PLAY_QUEUE_ITEM | args.item must still exist in source queue and require canPlayQueueItem |
| GET_ARTWORK | args.key from current state; bounded public-metadata JPEG/base64 with SHA256 key |

Library nodes have id/title/subtitle/browsable/playable. Responses include parent, page, revision and nextPage (null at end). A legacy source returning an unpaged result is bounded to 10,000 items then paginated on DX340. No arbitrary remote file paths. Item knowledge is bounded at 10,000 IDs. Removable-storage and library-change revision detection still require physical implementation/verification; session epoch alone is not a complete library revision.

Queue pagination is additive within v1. An empty GET_QUEUE args object still returns the first window. New clients request the returned nextOffset with the current revision; nextOffset is null at the end. offset is an integer0–10000; source queues above10000 return QUEUE_LIMIT. Each window has at most50 complete entries and at most48KiB of encoded UTF-8 data, leaving room for the reply envelope. Oversized metadata reduces the entry count; nextOffset advances by the actual count. A single entry that cannot fit returns MESSAGE_TOO_LARGE, never partial JSON or a silently truncated title. A changed source epoch/order/ID/media identity/title changes the queue revision; any supplied old revision or positive offset without the current revision returns STALE_LIBRARY. Refresh with offset0 and no revision to recover. PLAY_QUEUE_ITEM still validates the complete current queue and revision again after source handoff. No paging read starts playback. Clients replace the visible window rather than combining different revisions and show its range/total, Next queue page and Start of queue. Older hosts return no continuation; newer clients do not invent one.

SEARCH, SET_SHUFFLE and SET_REPEAT return UNSUPPORTED_CAPABILITY in this beta. Public metadata artwork is scaled/compressed to at most44KiB, identified by SHA256, and cached with bounds on both clients. Bulk replies have lower priority than controls; actual BLE latency remains unmeasured. canResume and canColdLaunch are false. Complete source-switch/audio acceptance remains outstanding.

ADJUST_VOLUME requires integer delta (-1 or1), integer expectedVolume and opaque profileId from the latest state's volume object, plus current host/source epochs and authorization. Public STREAM_MUSIC readback after500ms gives RESULT outcome observed, not acoustic proof. A local two-step listening check enables only the exact confirmed pair of device levels for that source/output/session. State adds current, hardware minimum/maximum, verified, verifiedMinimum/verifiedMaximum, outputLabel, profileId and reason. Units are device levels, not percentages or dB. Fields are additive in v1.

Volume proof is memory-only, bounded to8 contexts, and tied to source epoch, package version, firmware and output inventory. Stop, session-access loss or audio-device changes invalidate it; a hardware-wheel value outside the confirmed pair cannot become a remote baseline. Amp/gain/headphone changes cannot all be detected by Android and explicitly require rechecking. Only the selected source may be playing, with no other active session reported. The captured authorization lease and expected value/context are rechecked before a write and at readback; same-address reauthorization cannot revive old work. No volume retry, compensation or reconnect replay occurs. STALE_VOLUME needs fresh observation and a new deliberate action; VOLUME_PROFILE_CHANGED/VOLUME_VERIFICATION_REQUIRED need local verification; VOLUME_AT_BOUNDARY rejects steps outside the band. Errors include fresh state when possible. Physical phone/radio/other-output acceptance remains separate.

## Native browse metadata cache

Native BROWSE responses may add cached (boolean) and cacheAgeMs (nonnegative milliseconds). These describe presentation metadata only. The host retains at most200 pages of25 rows for less than10 seconds, scoped by source/source epoch/package version/parent/page. Cache hits require current authorization, permission, connected browser and retained item proofs; playability is derived from current capabilities. A root refresh (null parent/revision, or the native-root navigation token) queries the source and invalidates cached pages. Native PLAY_ITEM validation bypasses cache before and after source handoff. Changed/evicted identity, expiry, source/session/version changes and permission loss cannot turn cached rows into playback proof. Assisted UI browsing never uses this cache. Duplicate source IDs within a page return SOURCE_ID_AMBIGUOUS. Existing v1 clients can ignore the additive response fields.

## Playback source handoff

Apple assisted page revisions include the collection header, bounded full row identities/paths/downloaded flags, scroll path and Back availability. The collapsing toolbar's Back sibling position alone does not expire unchanged song rows. Each navigation action still validates its issued live path/signature; changed or newly visible rows, removed Back, moved/replaced tracks and window changes can return STALE_LIBRARY. Refresh explicitly before a new deliberate selection; no rejected playback mutation is replayed automatically.

SELECT_SOURCE changes the command target without starting playback. SET_PLAYING(true), PLAY_ITEM and PLAY_QUEUE_ITEM prepare playback by checking authorization, notification access, source identity/epoch and target validity before pausing a competing supported source. Preparation sends one pause and waits at most3.5s for the same session to report paused. Session replacement, lost authorization, changed target, unknown competing state or timeout prevents target start. Unsupported pause returns OTHER_SOURCE_PLAYING; failed observation returns SOURCE_HANDOFF_FAILED. The host holds mutation ownership throughout. Client request timeout still means unknown outcome; never automatically replay the command.

Item and queue identity/revision are checked again after handoff. Native item selection re-reads the parent and refuses to dispatch after its10s validation deadline. UI selection revalidates the visible downloaded row. A pause may already have succeeded when later validation fails: the previous source stays paused, and the user must issue a new deliberate command. No automatic rollback/resume or volume change occurs. A completed pause observation/dispatch does not establish acoustic silence, gapless switching or phone Bluetooth acceptance.

An already observed desired play/pause state is a no-op, including sources whose current action mask omits the redundant action. A real state-changing dispatch still requires the current capability. The host observes desired-state completion separately from library/queue item dispatch.

## Optional Apple Music UI-assisted browsing

The user accepted this mode's screen-on/unlocked requirement. It is opt-in and version-pinned to Apple Music6.5.3/code1599. Readiness is exposed through canBrowse/canPlayItem and browseMode=`ui-assisted`; ordinary session controls remain independent of UI readiness. Root BROWSE with null parent/revision navigates the public Library/Downloaded UI. Replies add uiAssisted=true, title, backId and a scroll-action parent token. Clients present this as a flat current screen: request backId with the current revision for Back, or parent/nextPage/current revision for forward scrolling. Root refresh recovers expired snapshots. Page sizes follow the visible source UI, bounded at50, and are not native25-item pages.

IDs bind service instance, active window, semantic snapshot and node path; revision must match the current snapshot before any navigation or play. Stale screens fail closed. Only rows bearing the source's Downloaded Song semantic badge are playable. No coordinate taps, gestures, download controls, sign-in forms or private app storage are used. Artist browsing is currently disabled pending model verification. A returned play dispatch is not proof of correct audible playback.

Mango's verified desired-state wrapper calls play only from observed paused state and pause only when required, with at most one callback and bounded state observation. Repeated desired state is a no-op. It avoids Mango's observed toggle-like raw repeated-play behavior. A timeout has unknown outcome and must not trigger automatic retry. This workaround is scoped to the tested app/firmware profile.

## Optional Mango local-folder mode

Mango native albums/artists/songs remain the default browse tree. When the user enables the separate Mango folder mode, the native root adds a `mango-ui:root` entry marked `uiAssisted:true`; it is browsable only while the assisted adapter is ready. State adds `canBrowseFolders`, `canPlayNativeItem` and `uiBrowseReason`; `browseMode` remains `direct` for the native tree. Clients decide assisted navigation from each response's `uiAssisted`, rather than assuming that every page for a source has the same mode. `canPlayItem` includes a ready assisted adapter; native item dispatch still requires its connected native browser and native capability/verification at initial validation, before handoff and at final dispatch. Native rows have `playable:false` until native selection is advertised or verified. The `nativeTestable` flag enables only the companion's explicit local diagnostic experiment, and must never enable phone playback.

Native item availability is not inferred from a MediaSession action bit when no native browse/revalidation path is connected. Clients must gate cached assisted actions separately from native capabilities: Apple uses its ui-assisted canBrowse readiness; hybrid Mango uses canBrowseFolders. On assisted readiness changes, discard assisted pages/pending browse context and require fresh browsing, preserving native pages/queues. Native capabilities must not reactivate a cached assisted file or optional folder entry whose service is absent.

Requesting `mango-ui:root` returns only Internal Storage and SD Card choices. Subsequent opaque IDs and revisions bind the service instance, window, semantic folder snapshot and exact row. Assisted responses use the same back/scroll contract as Apple mode. `mango-native:root` returns to native categories without reusing an assisted revision. No arbitrary path, Local Network or file editing action is accepted.

Existing Mango playlists have a separate optional `mango-ui:playlists` root row, also marked `uiAssisted:true`. It uses the same enabled/ready conditions as folders and resets navigation to the observed Playlist list; requesting this root requires page0. List rows are browsable, detail rows playable. The pinned parser binds the exact playlist name, total count, visible track positions/titles/artists, semantic list paths and window. Creation, Add To Playlist choosers, Play all, overflow menus and editing/deletion controls are not returned or dispatched. These are live visible-page proofs, not persistent file identities; no hidden file/codec or complete-library claim follows. The small two-track physical test does not verify long-playlist scrolling, duplicate files or post-rescan behavior.

Native public-item fingerprints include `MediaDescription.description` (the album on installed Mango), flags, media ID, title, subtitle and media URI. Nullable UTF-8 fields use explicit lengths before hashing; null is distinct from a literal string and delimiters in metadata cannot merge field boundaries. Native revision/parent validation and fresh pre-dispatch checks remain required. Software reused-ID regressions verify changed album descriptions invalidate proofs; physical SD/rescan acceptance remains separate.

Playlist visible pages may contain clipped edge containers with incomplete or absent labels. Such first/last containers have no returned actions; their available structure/identity is included in the page proof with explicit field/array lengths. Complete middle rows still require unique numeric positions and full title/artist metadata; incomplete middle rows or all-incomplete pages fail closed. The30 October source-local fixture verified all30 positions across six pages and explicit end, with one later-page audible selection after a metadata delay. This does not establish phone latency, multiple/duplicate playlists or arbitrary collection coverage.

Assisted-folder PLAY_ITEM additionally leaves/reopens the current folder through Mango before final dispatch: Mango can retain an old visible filename after an external rename/removal. The refreshed window/viewport fingerprint and selected live row must match. A retained matching scroll offset is accepted; otherwise continuation can restore up to the held logical page within a20-second preparation budget, with a deadline check before file click. Changed/missing proof fails stale. This navigation consumes assisted tokens and can take several seconds (one measured later-page preparation12.551s); it does not meet responsiveness acceptance. Native/playlist rescans, SD changes, same-name content replacements and real-phone behavior remain separately unverified.

The adapter is opt-in and pinned to Mango4.1.37/code240. DX340 must remain awake/unlocked. It uses semantic Accessibility node actions, sibling drawing order to exclude overlapping cached ancestor pages, stable navigation snapshots and fresh exact labels before dispatch. Ambiguous pages fail with UI_ACTIVE_PAGE_UNVERIFIED; changing trees may return UI_TREE_CHANGED, and wrong storage returns UI_STORAGE_CONTEXT_REQUIRED. Only sampled FLAC/WAV file types are enabled in this experimental mode; actual format/audio acceptance remains separate. PLAY_ITEM uses the shared observed source handoff, with no automatic retry.

Both UI adapters check current source epoch and controller authorization throughout navigation and before replying/acting. Revocation, source changes, service interruption and unbinding cancel or reject pending work. An already completed navigation/pause cannot be undone; no music is automatically resumed. These guards and local adapter tests do not establish either phone's physical BLE or security acceptance.

## Elapsed-position estimates (optional v1 fields)

`state.position` is milliseconds at host snapshot creation, normalized from the source's public PlaybackState position, speed and monotonic last-update time. `-1` means unknown. `duration` remains source metadata in milliseconds. New hosts include optional `playbackSpeed`: positive finite rates up to16 only while the source reports playing, with a known position/duration and valid source timestamp; otherwise0. Projection clamps to duration. These fields describe source estimates, never audible-output observations. Android and phone monotonic timestamps must not be compared across devices.

Controllers may advance a labelled estimate locally between source events without requesting periodic state messages. Old hosts without speed remain fixed snapshots. Never infer a next track at duration, enable seeking from the estimate alone, or replay a command when the estimate becomes stale. Actual elapsed accuracy, latency and source/phone recovery still need physical tests.

## Native browse cancellation and session access

Native page requests bind authorization, source epoch and browser instance through completion. After timeout/cancellation, callbacks may not alter cached item/proof/revision data. Detected notification-access loss cancels pending native pages, invalidates source callbacks and item IDs, advances source epochs and disables advertised capabilities. Restoring access requires fresh discovery/observer registration and source state; old requests remain terminal. GET_STATE/SUBSCRIBE_STATE explicitly refreshes that discovery without playback or restarting the companion. These are implementation rules, with physical permission/BLE delivery still subject to acceptance tests.


### Pinned Mango native playback-ID translation

Mango4.1.37/code240's public browser emits one-based row suffixes while its playback callback consumes the suffix as a zero-based list index. The host validates the original native ID/parent/title proof and both fresh source reads, then translates only the final dispatch ordinal to ordinal−1 for the known All Music/Now Playing/nested Album ID shapes. Client-visible IDs/revisions are unchanged; clients must not translate them. Unknown versions/formats, mismatched parent/display ordinal and overflow fail before dispatch. Raw-ID listening approval does not verify this corrected scheme; a fresh owner confirmation is required and invalidates the old source revision. One corrected native-album title has local experiment and production audio confirmation; this is not full native-category/phone acceptance.
